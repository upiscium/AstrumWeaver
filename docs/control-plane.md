# Durable Control Plane

AstrumWeaver's Control Plane owns durable scheduling state. Workload-specific execution remains behind the Worker/Executor boundary.

## Durable entities

v0.1 persists two core entities:

- Workers
- Jobs

Worker state includes topology/resource facts, capability advertisement, liveness, drain/offline state, and scheduler capacity.

Job state includes the requested capability, opaque payload, generic resource requirements, priority/FIFO sequence, retry state, worker ownership, lease fencing, and generic JobResult data.

## Job ordering

Eligible jobs are selected by:

1. priority descending
2. durable sequence ascending

The sequence is generated by the durable store so FIFO behavior remains explicit even when multiple jobs have identical timestamps.

## Atomic claim

The PostgreSQL backend uses row locking and FOR UPDATE SKIP LOCKED to allow concurrent schedulers/workers to claim jobs safely.

A claim is only accepted when:

- the worker is ONLINE
- the worker heartbeat is not stale
- active jobs are below max concurrency
- the job capability is advertised by the worker
- all generic JobRequirements match the WorkerSpec
- the job is available
- retry budget remains

The job is then assigned a fresh lease token and lease expiry.

## Lease fencing

Every running attempt receives a unique lease token.

Worker terminal transitions must provide:

- job ID
- worker ID
- current lease token

A stale token cannot complete or fail a job after that attempt was recovered and re-claimed.

Lease expiry is checked at terminal-transition time even if the recovery loop has not run yet.

## Recovery

Expired running jobs are recovered one at a time under row lock.

If retry budget remains, the job returns to QUEUED with a new availability time. Otherwise it becomes FAILED.

Worker active-job capacity is decremented as part of the same durable transition.

## Heartbeat and TTL

Worker heartbeats update last-seen state and may renew the lease of one explicitly identified active job when the matching fencing token is supplied.

The repository never trusts a worker-reported active-job count. Active capacity is derived from authoritative running job ownership.

Workers that exceed the configured TTL are marked OFFLINE and cannot claim new work. Their existing job attempts are released only through normal completion/cancellation or lease-expiry recovery.

## Draining

DRAINING workers do not receive new jobs. Existing running jobs may finish and continue renewing their lease.

This is the basis for later borrowable-development-worker support.

## GPU ownership

Registration rejects overlapping GPU UUID ownership while another worker is ONLINE/DRAINING or still has active jobs.

A worker with active jobs may not change its resource/topology declaration during re-registration.

This protects the scheduler-visible exclusive compute-unit contract.

## Resource matching

The durable PostgreSQL claim query implements the same semantics as the pure matcher:

- worker class
- requested capability
- additional required capabilities
- required labels
- optional GPU UUID pinning
- minimum GPU count
- minimum total VRAM
- minimum single-device VRAM

A 2 x 12 GiB worker therefore does not satisfy a 20 GiB single-device requirement.

## Idempotency

Job submission may include an idempotency key.

Replaying an equivalent submission returns the existing job. Reusing the key for a different capability, payload, constraints, priority, retry policy, or explicit availability time is a conflict.

## PostgreSQL schema

The schema is versioned by ordered SQL migrations, beginning with:

- migrations/000_schema_migrations.sql
- migrations/001_control_plane.sql
- migrations/002_worker_accelerators.sql

`schema_migrations` is the canonical applied-version ledger. The Control readiness check compares that ledger with the migration files packaged with the running binary, so starting a newer binary against an older unmigrated database remains Not Ready until `astrumweaver-migrate` succeeds.

PostgreSQL is the production durable backend for v0.1. The in-memory repository exists as a deterministic reference backend for unit tests and contract development; production setup must not silently fall back to it.

## Generic result persistence

Job results use the provider-neutral JobResult contract. Structured outputs, artifact references, metrics, optional text, and executor metadata are serialized into JSONB without teaching the Control Plane application-specific semantics.

The old LLM-specific model-profile and Ollama assumptions are intentionally absent.

## Lock ordering

Whenever a transaction touches both a job and a worker, AstrumWeaver uses the lock order:

job -> worker

Heartbeat renewal follows the same order.

This avoids introducing a worker/job lock inversion between claim, completion, failure, cancellation, recovery, and heartbeat paths.
